# Content-first UI

콘텐츠의 의미를 먼저 결정하고 기존 디자인으로 표현한다. 디자인 디테일의 선택은 최소화하되, 필요한 정보를 표현하는 능력까지 줄이지 않는다.

## 적용 범위

- 새 화면·섹션을 만들거나 정보구조·배치를 변경할 때 항상 적용한다. 화면 생성 도구를 구현할 때도 이 순서를 생성 지침에 연결한다.
- 실행 여부는 사용자 요청을 따른다. 논의 중에는 설계 판단까지만 하고, 이 스킬 자체를 코드 수정·게시·외부 작업의 승인으로 삼지 않는다.
- 기존 디자인을 정확히 이식하는 작업은 그 디자인에 이미 담긴 아래 결정을 복원하고 보존한다. 임의 재설계하지 않는다.
- 작은 수정은 영향을 받는 콘텐츠와 섹션에만 적용한다. 매번 전체 화면을 재설계하거나 별도의 계획 문서를 만들 필요는 없다.

## 반드시 지킬 순서

### 1. 노출할 콘텐츠 결정

사용자 요청과 확보한 데이터에서 사용자가 알아야 할 내용을 정한다. 핵심 정보, 보조 정보, 반복되는 대상과 실제 상태를 구분한다. 이 단계에서 카드·템플릿·레이아웃부터 고르지 않는다.

콘텐츠가 어떤 도메인의 어떤 대상인지, 사용자가 무엇을 판단하거나 하려는지 먼저 이해한다. 제목·날짜·숫자라는 타입에 더해 날짜가 마감인지 조회 기간인지, 숫자가 가격인지 식별자인지처럼 업무상 의미와 대상 간 관계를 파악한다. 같은 도메인에서도 소개·탐색·비교·입력은 구분한다.

없는 상태·수치·기능을 화면을 채우기 위해 만들지 않는다. 샘플 요청에는 샘플임을 구분한다. 기존 내용을 바꾸는 요청에서는 변경하지 않을 정보를 보존한다.

콘텐츠(무엇을 읽고 판단하는가), 컨트롤(무엇을 선택·입력·변경·실행하는가), 상태(대상이나 조작이 지금 어떤 상태인가)를 구분한다. 콘텐츠의 읽는 순서를 먼저 잡고, 실제 필요한 컨트롤을 적용 대상과 연결한다. 카드나 예제를 조작 가능하게 보이게 하려고 버튼·입력·하단 행동 영역을 의무적으로 붙이지 않는다.

### 2. 콘텐츠 특성에 따라 기존 컴포넌트 매핑

[컴포넌트 매핑 결정트리](references/component-mapping-tree.md)를 읽고 영향을 받는 콘텐츠에 적용한다. 먼저 해당 도메인에서 익숙한 정보 표현과 어포던스(무엇을 읽고 누르고 바꿀 수 있는지 드러내는 단서)를 검토한다. 읽기·비교·선택·입력·실행·이동·보기 전환을 구분하고, 표시 상태와 조작 결과를 혼동하지 않는다. 도메인의 관습은 기존 사례를 찾는 기준이며 새로운 기능·배치·스타일을 임의로 만드는 근거가 아니다.

아이콘도 컴포넌트를 확정하기 전에 검토한다. 대상 식별·출처·상태·행동 중 무엇을 알려야 하는지 정하고, 기존 디자인의 같은 역할과 실제 자산·등록 키를 확인한다. 서비스 로고, 일반 기능 아이콘, 상태 표식과 인물 아바타의 역할을 구분하며 색·크기·배치는 원본을 따른다. 아이콘이 필요한 자리가 아니면 생략하고, 필요한 의미의 자산이 없으면 공백으로 알린다. 이름만 비슷한 아이콘, 이모지, 직접 그린 SVG로 메우지 않는다.

각 정보의 의미에 맞는 기존 표현을 찾는다. 예를 들어 이름은 제목, 맥락은 설명, 분류는 태그, 상태는 배지로 표현할 수 있지만 실제 매핑은 해당 디자인 시스템의 사용례를 따른다. 모든 요소에 태그·배지·아이콘을 붙이는 체크리스트로 쓰지 않는다.

카탈로그와 실제 사용 화면·Story·디자인 정본을 확인해 컴포넌트, 허용된 props, 시각적 사용례를 연결한다. 실제 컴포넌트 경계가 완성 블록이면 그 블록의 기존 입력·slot에 매핑하고 내부를 임의 재구현하지 않는다.

구현이 승인되면 선택한 기존 조합에 요청된 데이터·행동을 연결한 최소 동작부터 확인한다. 이 시도는 실제 작업의 첫 구현이며 별도 데모·카탈로그·승인 단계를 만들지 않는다. 표현이 부족하다는 판단은 어떤 입력·조작이 기존 계약으로 충족되지 않는지에 근거한다. 계약에서 부적합함이 이미 명확하면 그 근거로 판단하고 억지로 연결하지 않는다. 실행 불가는 미검증이지 capability 부재의 증거가 아니다. 논의만 요청된 경우에는 계약과 사용례 대조까지만 한다.

화면 조합이나 컴포넌트 체계를 설계하는 작업에서는 [구성 단위와 의미 있는 옵션](references/component-composition.md)을 읽는다. 도메인 이름으로 카드 종류부터 고르지 않고, 컬렉션·항목·상세·보조 속성·행동의 책임을 구분한다. 기존 정본의 슬롯과 옵션을 사용하며, 시스템 확장이 요청된 경우에만 소유 모듈에서 부족한 계약을 확장한다.

C* 작업이면 이 단계에서 [기존 디자인 카탈로그 참조법](references/cstar-catalog.md)을 읽는다. A2UI를 위해 정리된 사례도 데이터와 표현의 관계를 참고하는 디자인 자료로 사용하며, 출력 형식을 A2UI로 강제하지 않는다.

### 3. 관련 데이터 그룹핑과 배치

같은 대상을 설명하는 정보를 묶고, 반복 항목과 서로 비교할 정보를 구분한다. 주정보와 보조 정보의 관계, 반복 행의 구조, 그룹 경계를 정한 뒤 기존 디자인의 배치·조합 규칙으로 섹션을 구성한다.

각 요소가 그 위치에 있어야 하는 이유를 사용자 판단·행동과 연결한다. 콘텐츠는 정보 위계와 읽기 관계로, 컨트롤은 적용 범위·사용 시점·관련 명령의 관계로 묶는다. 둘을 항상 떨어뜨리거나 같은 박스에 넣지 않는다. 선·면·간격은 이 관계를 정한 뒤 선택하며, 컨트롤의 외형 규칙을 콘텐츠 전체에 적용하지 않는다. 구체적인 판단은 [구성 단위와 의미 있는 옵션](references/component-composition.md#콘텐츠와-컨트롤의-조립)을 따른다.

사용자가 항목을 알아보고 판단하는 필드를 주정보에 매핑한다. 문의 제목·품목명으로 찾는 과업이면 그 이름이 주정보이고 ID·출처는 보조 정보다. 식별번호 자체로 대상을 찾는 과업에서는 그 번호의 위계를 보존한다. 표에 기존 main·meta·action 열 역할이 있으면 콘텐츠 역할로 매핑하며 폭 수치를 직접 정하지 않는다.

기존 컴포넌트를 썼다는 사실만으로 새로운 조합을 임의 설계하지 않는다. 그룹의 의미는 콘텐츠에서, 시각적 배치 근거는 기존 디자인이나 사용자가 지정한 구조에서 가져온다.

### 4. 최소한의 정보성 문구 보충

콘텐츠와 그룹만으로 뜻이 불명확한 곳에 제목·짧은 설명·단위·범위 등을 보충한다. 제목 반복, 장식적인 소개 문구, 근거 없는 요약 수치와 기능 안내는 넣지 않는다. 카피를 먼저 만들고 데이터를 끼워 맞추지 않는다.

서로 다른 필터의 전체 선택은 '전체 상태'·'전체 담당자'처럼 범위가 구분되어야 한다. 작성 도구의 미지원 기능과 기술 진단은 에이전트 대화에서 설명하고, 생성한 앱에는 사용자 과업과 데이터에 필요한 문구를 둔다. UI 실험의 샘플 표시는 짧게 유지한다.

### 5. 섹션 전체 재배치

구성된 섹션을 중요도와 읽는 흐름에 따라 재배치하고, 중복된 내용을 합치거나 덜어낸다. 기존 디자인의 전체 배치와 반응형 규칙 안에서 정보 밀도와 흐름을 확인한다. 사용자에게서 이미 확정된 순서·구조는 보존한다.

## 디자인 제약과 부족한 표현

- 기존 디자인의 컴포넌트·토큰·허용된 조합만 사용한다. 색·폰트·간격·너비·정렬·모서리·아이콘을 자의적으로 새로 정하지 않는다.
- 카탈로그에 맞추려고 중요한 정보를 버리거나, 의미가 다른 props에 억지로 넣거나, 모든 콘텐츠를 요약 카드로 바꾸지 않는다.
- 필요한 표현이 없으면 어떤 콘텐츠를 어떤 기존 표현으로 나타낼 수 없는지 구체적으로 알린다. 임의 신규 컴포넌트·CSS·미등록 요소로 메우지 않는다. 기존 표현의 재사용 경계 확장이 필요하면 그 범위를 드러낸다.
- 구현 언어는 콘텐츠 판단을 대신하지 않는다. React·HTML·A2UI·동적 도구 모두 같은 순서를 따른다.

## 결과 확인

렌더링된 화면에서 콘텐츠 누락, 도메인의 사용자 과업에 맞는 표현, 예상 행동과 일치하는 어포던스, 아이콘의 의미, 그룹의 경계, 문구의 필요성, 섹션의 읽는 순서를 확인한다. 디자인 정본과 같은 조건으로 시각적 위계·밀도·반응형 상태를 대조한다.

스키마 검증·타입 검사·넘침 없음은 디자인 품질 검증과 구분한다. 실제 화면을 확인하지 못했거나 필요한 표현이 부족하면 그 범위를 명시한다. 사용자에게는 필요한 결정과 결과만 간결히 전달하며 내부 판단 과정을 장문으로 출력하지 않는다.

## 리서치 기반 개선 루프

화면 생성 품질을 개선하는 요청에서는 정본 사례와 생성 결과를 같은 조건으로 비교한다. 컴포넌트 연결·DOM 일치·타입 검사는 구현 근거이며, 화면 구성의 품질 판정을 대신하지 않는다. 원본 사례가 선택한 위계·정보 밀도·그룹 경계·읽는 흐름을 확인하고, 생성 결과에서 지나친 반복·늘어진 상세·좁아진 주정보·빠진 어포던스를 찾는다.

실패 원인을 콘텐츠 해석, 컴포넌트 연결, 기존 조합의 전달, 런타임 표현 공백으로 구분한다. 시각 선택을 막았는데 대신 쓸 기존 조합도 제공하지 않은 경우에는 선택지를 임의로 열지 말고 정본의 조합·variant를 정확한 출처로 선택할 수 있게 연결한다. UI 전용이라는 이유만으로 요청된 입력 디자인을 텍스트로 없애지 않는다. 표현 가능한 상태와 실제 업무 동작을 구분한다.

한 번의 개선 단위는 실패 확인 → 해당 원인의 도구·지침 수정 → 같은 데이터 재생성 → 원본과 재비교로 완료한다. 반복 원인만 공통 지침에 반영하고, 다른 도메인의 샘플로 특정 사례에만 맞춘 개선인지 확인한다. 원본과 가까워졌다는 주장에는 실제 비교 증거를 남기고 미검증 부분을 구분한다. 제약 내에서 해결할 수 없는 표현은 임의 디자인으로 덮지 않는다.

참고: [Impeccable polish](https://github.com/pbakaus/impeccable/blob/main/.agents/skills/impeccable/reference/polish.md)의 기존 시스템 보존·원인별 분류·실제 화면 검수 원칙과 [Anthropic frontend-design](https://github.com/anthropics/skills/blob/main/skills/frontend-design/SKILL.md)의 콘텐츠 기반 구성·시각적 자기 검수 원칙을 적용한다. 외부 스킬의 신규 시각 창작·별도 브라우저·자동 설치 지시는 이 지침에 포함하지 않는다.

## 컴포넌트 선택과 capability 공백

컴포넌트 이름보다 사용자가 수행하는 일을 기준으로 선택한다. 정보를 읽는가, 값을 입력하는가, 데이터를 바꾸는가, 다른 화면으로 이동하는가, 보기를 바꾸는가, 결과나 상태를 확인하는가를 구분한다. 같은 버튼 표현이어도 액션 실행과 페이지 이동은 서로 다른 계약이다.

도구·카탈로그의 실제 동작 계약을 읽어 표현과 capability를 함께 확인한다. 이미 지원하는 선택·바인딩·즉시 저장을 누락한 채 기능이 없다고 단정하지 않는다. 기존 API가 부족하면 표현·조합·동작 중 무엇이 빠졌는지 분리해 알린다. 검색 입력이 있다고 목록 필터링이 되는 것은 아니며, 탭이나 이동 버튼이 있다고 페이지 전환이 되는 것은 아니다. 실제 동작을 연결할 수 없는 컨트롤을 완성된 기능처럼 노출하지 않는다. 기존 정본 확장으로 해결 가능한지 먼저 확인하고, 독립된 책임이 확인될 때 새 컴포넌트군을 등록한다.

에이전트가 실행 가능한 화면을 만드는 경우 등록 스킬과 데이터의 입력·출력 필드 및 타입을 읽고 맞춘다. 프롬프트 문구로 고정 스킬의 capability가 바뀐다고 가정하지 않는다. 화면 생성 성공과 실행 성공을 구분하며, 저장·실행·페이지 전환을 실제로 확인하지 않았다면 그 범위를 명시한다.

## MOCK 기반 비교 실험

도메인에 맞는 화면을 실험할 때는 외형보다 사용자 과업과 데이터 관계를 바꿔 비교한다. 예를 들어 문의 처리는 상태와 응답을, 재고 관리는 수량·단위·품절을 보존해야 한다. 모든 도메인을 같은 요약 카드 구조로 환원하지 않는다. 한 레코드의 여러 필드를 비교해야 할 때는 행 관계가 유지되는 목록·표를 사용한다. 서로 독립된 필드별 목록을 나란히 놓아 행 관계를 대신하지 않는다. 카탈로그에 필요한 표현이 없다면 한 대상의 목록·상세 확인과 여러 대상의 비교를 구분해 가능한 범위를 알린다.

요청 범위 안에서 긴 이름·본문, 0과 빈 값, 서로 다른 상태 같은 실제 차이가 있는 MOCK으로 읽기와 동작을 확인한다. 0을 누락이나 미입력으로 오해하지 않고 빈 값과 구분한다. 기존 사용자 데이터는 보존하고 실험 데이터의 저장 공간을 구분한다. 발견한 실패와 개선 후 관찰을 나누어 기록하고, 반복되는 원인만 공통 지침에 반영한다. 한 사례의 배치를 보편적인 디자인 규칙으로 굳히지 않는다.
