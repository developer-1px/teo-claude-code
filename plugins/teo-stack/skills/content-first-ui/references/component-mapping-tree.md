# 콘텐츠 → 기존 컴포넌트 매핑 결정트리

콘텐츠를 정한 뒤, 그룹과 레이아웃을 만들기 전에 사용한다. 도메인·사용자 과업·데이터 관계에서 표현 후보를 찾고 실제 디자인 사례와 현재 작성 도구의 지원 범위로 확정한다. 이 문서의 컴포넌트 이름은 C* 디자인 카탈로그의 후보이며 React 작성 허용 목록이 아니다. 다른 디자인 시스템에서는 같은 역할의 실제 정본으로 매핑한다.

## 1. 컴포넌트를 고르기 전: 의미와 도메인

각 콘텐츠 묶음에 대해 아래 내용을 파악한다. 짧은 작업은 별도 문서 없이 판단해도 된다.

| 확인할 것 | 판단 예시 |
|---|---|
| 대상과 관계 | 일정과 참석자, 문의와 답변, 상품과 옵션, 문서와 출처 |
| 사용자 과업 | 읽기, 찾기, 비교하기, 선택하기, 작성하기, 실행하기 |
| 필드의 실제 의미 | 날짜 = 작성일 / 마감 / 조회 기간, 숫자 = 수량 / 가격 / 식별자 |
| 중요한 구분 | 사실과 해석, 값과 단위, 상태와 상태 변경, 0과 없음과 아직 모름 |
| 도메인의 익숙한 단서 | 일정의 시간축, 비교의 같은 기준, 설정의 현재 값과 변경 수단 |
| 판단 근거 | 사용자 요청, 실제 데이터 계약, 같은 과업을 표현한 기존 디자인·제품 사용례 |

도메인 이름만으로 페이지 템플릿을 정하지 않는다. 영화 소개와 상영 시간표는 같은 도메인이어도 서로 다른 과업이다. 관습에서 떠올린 필터·정렬·예약·별점도 실제 콘텐츠와 요청에 없으면 추가하지 않는다.

## 2. 어떤 어포던스가 필요한가?

```text
사용자가 이 콘텐츠로 하려는 일은?
|
+-- 정보 읽기 / 상태 확인
|   +-- 제목·설명·값·상태의 위계를 구분한다 -> 3번
|   '-- 조작을 암시하는 입력·화살표·버튼은 실제 역할이 있을 때만 둔다
|
+-- 대상 비교 / 차이 판단
|   '-- 비교 기준·단위·기간을 맞춘다 -> 4번
|
+-- 대상 선택 / 값 입력 / 설정 변경
|   +-- 현재 상태만 보여주는가? -> 읽기 분기로 돌아간다
|   +-- 항목 선택 / 동의 -> 기존 Checkbox 사용례
|   +-- 하나의 값 선택 -> RadioGroup / Select / 단일 선택 MultiSelect 사용례
|   +-- 여러 값 선택 -> MultiSelect 또는 기존 체크박스 그룹 사용례
|   +-- 켜기·끄기 설정 -> Switch 사용례
|   +-- 짧은 글 / 긴 글 / 수량 -> TextField / TextArea / NumberField
|   '-- 대상 담기와 후보 추천 -> SlotGroup / SuggestList 사용례
|
+-- 작업 실행 / 다른 위치로 이동
|   '-- 기존 동작·이동 컴포넌트의 구분, 라벨, 아이콘, action 계약을 확인한다
|       실행과 이동을 버튼 모양만 보고 같은 기능으로 취급하지 않는다
|
'-- 보기 전환 / 검색 / 정렬 / 필터
    '-- Tabs / SearchField / SortDropdown 등 해당 역할의 기존 사용례를 찾는다
        값 선택과 보기 전환을 구분하고 실제 연결 가능한 범위를 확인한다
```

RadioGroup과 Select 중 선택은 선택지의 가시성·길이·설명 필요성 및 기존 사용례로 판단한다. 임의의 항목 수 기준을 새 규칙으로 만들지 않는다. UI 전용 실험은 요청된 조작의 모양과 상태를 표현할 수 있지만 저장·검색·업무 실행까지 완성했다고 설명하지 않는다.

## 3. 개별 정보는 무엇을 뜻하는가?

```text
정보의 의미
|
+-- 대상 이름 / 섹션 이름 -> 기존 제목 slot 또는 Text의 해당 variant
+-- 설명 / 출처 / 보조 맥락 -> 기존 description·meta slot 또는 Text
+-- 상태 / 분류 -> 기존 Badge 사용례; 상태·분류별 시각 규칙 보존
+-- 조회 날짜 / 기간 -> DateChip 사용례; 표시와 날짜 입력을 구분
+-- 인물 식별 -> Avatar + 이름의 기존 조합
+-- 브랜드 / 서비스 출처 -> 실제 등록 로고·서비스 자산 -> 5번
+-- 이미지가 핵심인 대상 -> StaticImage / PosterHero / MediaThumb 사용례
|
+-- 숫자 / 진행 정보
|   +-- 식별자·일반 속성 -> 본문 또는 기존 label-value 표현
|   +-- 핵심 수치·단위·기준 -> Metric 사용례
|   +-- 실제 비율 -> Meter 사용례
|   +-- 순서가 있는 단계 -> StepBar 사용례; 단계 이동 기능은 별도 확인
|   '-- 남은 시간 -> RingTimer 사용례
|
+-- 근거 있는 해석 -> 사실과 구분된 InsightCard 사용례
'-- 결과가 비어 있음 -> 확정된 empty에만 EmptyState 사용례
    로딩·오류·미확인 상태는 각각의 기존 상태 표현을 확인한다
```

완성 블록이 제목·메타·아이콘을 소유하면 해당 입력에 매핑한다. 내부를 개별 Text와 아이콘으로 다시 조립하지 않는다. 제목·태그는 정보 역할이며 새 `Title`·`Tag` 컴포넌트를 만들어도 된다는 뜻이 아니다. 숫자가 있다고 전부 Metric으로, `boolean`이라고 전부 Switch로 바꾸지 않는다. 단계·시간을 임의의 퍼센트로 환산하지 않는다.

## 4. 여러 정보가 어떤 관계인가?

```text
관련 데이터 묶음
|
+-- 한 대상의 정체성과 속성 -> 대상 상세의 기존 제목·이미지·속성 조합
+-- 반복 항목
|   +-- 같은 열을 따라 상세 값 확인 -> DataTable
|   +-- 제목·출처·후속 내용 읽기 -> NoteList 사용례
|   +-- 이름·메타·오른쪽 값 확인 -> TxList 사용례
|   '-- 단순 서술 나열 -> List 사용례
|
+-- 대상 간 차이를 동일 기준으로 판단 -> CompareTable 사용례
+-- 날짜·시각·기간이 관계의 중심
|   +-- 시간축의 개별 일정 -> Agenda / AgendaRow 사용례
|   '-- 하루 일정 요약 -> DateChip / SlotPlate 사용례
|
+-- 수치의 관계를 시각적으로 판단
|   +-- 시간에 따른 추이 -> LineChart
|   +-- 범주별 양 비교 -> BarChart
|   '-- 기존 수치·행에 붙는 작은 추이 -> SparkLine
|
+-- 순서가 있는 이미지·장면 -> 기존 미디어 연속 표현 사례
'-- 맞는 후보를 찾지 못함 -> 전체 카탈로그와 같은 과업의 제품 화면 탐색
    그래도 없으면 필요한 표현의 공백을 알린다
```

각 잎은 후보를 찾는 출발점이다. 하나의 섹션이 여러 관계를 가지면 핵심 과업을 먼저 표현하고 보조 정보는 해당 원본의 slot에 둔다. 상세 값을 읽어야 하는데 차트로 대체하거나, 원본에 없는 지표·추이를 생성하지 않는다. 전문 차트·도메인 전용 표현은 전체 카탈로그에서 데이터 계약과 실제 사례를 추가 확인한다.

이 단계에서는 표현 후보만 정한다. 실제 Row·Column·Grid·Card 선택, 그룹 경계와 섹션 순서는 스킬의 다음 단계에서 원본 조합을 확인해 정한다.

## 5. 아이콘은 어떤 의미를 전달해야 하는가?

아이콘의 역할은 어포던스와 함께 먼저 검토하고, 컴포넌트 후보를 찾은 뒤 정확한 자산과 slot을 확정한다.

```text
아이콘이 전달할 의미가 있는가?
|
+-- 사람 / 브랜드 / 데이터 출처 식별
|   '-- Avatar / 등록 로고 / 해당 서비스 자산의 기존 사용례
|
+-- 행동 예고(추가·검색·삭제·펼침 등)
|   '-- 같은 행동의 기존 컨트롤 + 등록 기능 아이콘
|       실제 행동·상태와 일치하는지, 라벨과 접근 가능한 이름 확인
|
+-- 상태 구분(완료·주의 등)
|   '-- 같은 상태의 기존 표식과 텍스트; 색·아이콘만으로 뜻을 전달하지 않는다
|
+-- 콘텐츠 종류 / 도메인 식별
|   '-- 동일 의미의 기존 사용례가 있을 때 그 자산·위치·크기를 따른다
|
'-- 식별·이해·조작에 추가하는 의미 없음 -> 선택적인 아이콘은 생략

후보를 찾았는가?
+-- 예 -> 실제 등록 키 + 렌더되는 자산 + 현재 도구의 slot 지원 확인
'-- 아니오 -> 기존 텍스트로 의미를 보존할 수 있는지 확인
    필수 표식이거나 원본 구성을 충족하지 못하면 지원 공백을 알린다
```

- 같은 도메인이라는 이유로 모든 항목에 같은 아이콘을 붙이지 않는다. 같은 역할에는 일관된 자산을 쓴다.
- 서비스 로고는 실제 출처·연결 대상을 식별한다. 일반적인 메일·일정 기능을 그 서비스의 기능처럼 표시하지 않는다.
- C* `SemanticIcon`은 일반 기능 아이콘과 다른 3D 자산 매핑을 사용한다. 이름 문자열이 유효해 보여도 의도한 자산인지 원본을 확인한다.
- 알 수 없는 이름이 기본 아이콘으로 렌더되거나 브랜드가 기본 로고로 대체되어도 성공으로 취급하지 않는다. 이모지·외부 아이콘 묶음·직접 그린 SVG·자의적 색상으로 메우지 않는다.
- 기존 디자인이 소유하는 장식·아이콘을 임의 제거하는 재설계로 확대하지 않는다. 의미가 불명확하면 같은 역할의 원본을 더 확인한다.

## 6. 실제 컴포넌트로 확정하는 마지막 분기

```text
콘텐츠 의미 + 사용자 과업 + 표현 후보 + 필요한 아이콘
|
+-- 같은 역할의 원본 사례가 있는가?
|   +-- 예 -> 실제 props·slot·자식 구조·상태·아이콘 조합을 읽는다
|   '-- 아니오 -> 전체 카탈로그 탐색 -> 없으면 근거/표현 공백으로 알린다
|
+-- 현재 작성 도구가 그 표현과 입력을 지원하는가?
|   +-- 예 -> 실제 필드와 정확한 컴포넌트 입력을 매핑한다
|   '-- 아니오 -> 필요한 표현·조합·동작 중 빠진 부분을 구체적으로 알린다
|       미등록 이름 출력, 임의 CSS, 조용한 렌더러 전환은 하지 않는다
|
'-- 관련 데이터 그룹핑·배치 -> 최소 정보성 문구 -> 섹션 전체 재배치
```

C*에서는 [카탈로그 참조법](cstar-catalog.md)에 따라 `patterns`로 후보를 찾고 `read`로 관련 원본 1~3개를 읽는다. 목차에 없으면 `list`로 범위를 넓힌다. React는 별도로 `react_screen`의 `catalog`·`inspect`를 확인한다. 디자인에 있는 컴포넌트와 현재 도구로 작성 가능한 컴포넌트를 구분한다.

필요한 경우 `콘텐츠 필드 → 도메인상 의미 → 사용자 과업/어포던스 → 원본 컴포넌트·slot·아이콘 → 현재 지원 여부` 정도만 기록한다. 이 기록을 필수 화면 요소나 별도의 UI 프로토콜로 만들지 않는다.

## 같은 데이터에서 달라지는 판단 예시

| 콘텐츠 | 사용자 과업과 어포던스 | 찾아볼 기존 표현 |
|---|---|---|
| 날짜 | 자료의 조회 기간 확인 | `DateChip`; 달력 모양을 날짜 선택 기능으로 설명하지 않음 |
| 날짜·시각·일정명 | 시간순으로 일정 파악 | `03_calendar-day`의 `Agenda`·`AgendaRow` |
| 설정의 켜짐 여부 | 현재 값을 보고 변경 | `10_notification-permission`의 제목·설명·`Switch` |
| 작업의 완료 여부 | 완료 상태 읽기 또는 완료 처리 | 읽기는 기존 상태 표현, 변경은 `07_task-card`의 체크박스 사용례와 실제 계약 확인 |
| 같은 속성의 여러 대상 | 레코드 상세 확인 / 대상 간 비교 | `31_incremental-dashboard`의 `DataTable` / `24_agent-realestate`의 `CompareTable` |
| 영화 제목·이미지 / 상영 시각 | 작품 소개 / 시간표 파악 | `29b_movie-card-full` / `03_calendar-day`의 데이터·표현 관계 참고 |
| 제목·출처·후속 내용 | 출처를 구분하며 읽기 | `26b_agent-minutes-briefing`의 `NoteList`; 실제 출처일 때만 해당 서비스 아이콘 |

예시는 필수 기능 목록이 아니다. 원본의 업무명·샘플 값·버튼을 그대로 복사하지 않고 요청된 콘텐츠와 과업에 해당하는 역할만 매핑한다.
