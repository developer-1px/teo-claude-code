# 구성 단위와 의미 있는 옵션

컴포넌트 체계를 만들거나 화면의 여러 데이터 묶음을 조합할 때 사용한다. 특정 제품의 배치를 모든 도메인의 템플릿으로 강제하지 않는다.

## 데이터에서 구성으로

먼저 사용자 과업과 실제 데이터 관계를 짧은 트리로 정리한다. 단순한 수정에는 별도 트리가 필요 없다.

```text
작업 목적
├─ 탐색할 컬렉션
│  └─ 항목: 정체성 / 요약 / 상태 / 보조 맥락
├─ 선택한 항목의 상세: 본문 / 편집 / 주요 행동
└─ 보조 속성: 선택 대상과 연결된 값 / 필요한 변경 수단
```

각 묶음이 왜 필요한지, 어떤 관계로 함께 읽히는지를 정한 뒤 실제 정본 API에 매핑한다. 트리에 있는 모든 노드를 화면에 표시할 필요는 없다.

| 구성 단위 | 책임 | 의미 있는 선택 |
|---|---|---|
| 컬렉션 | 탐색·비교·선택 | 목록/테이블/갤러리, 실제 단일·다중 선택 capability |
| 항목 | 빠른 식별과 판단 | 선행 표시, 제목·요약, 후행 상태, 메타데이터 슬롯 |
| 상세 | 선택 대상 읽기·작업 | 본문, 읽기·편집 표현, 연결된 행동 |
| 인스펙터 | 주 콘텐츠를 보조하는 속성 | 대상 연결, 열림·닫힘, 기존 읽기·쓰기 컴포넌트 |
| 그룹 | 관계와 경계 | 기존 간격, 구분선, 의미 있는 표면 |
| 행동 영역 | 대상에 적용할 명령 | 실제 실행·이동·저장 계약 |

항목의 선택·키보드·정렬 책임을 요약 컴포넌트에 복제하지 않는다. 읽기와 쓰기는 무조건 같은 컴포넌트의 mode prop으로 합치지 않는다. 기존 정본의 데이터 표현과 입력 계약이 별개라면 해당 슬롯에 각각 조합한다.

시스템 확장이 요청된 경우 도메인 중립적인 정본은 반복되는 구조와 책임을 소유하고, 도메인별 사례는 필드 매핑·문구·정책을 소유한다. 모든 목적을 포괄하는 컴포넌트 하나나 임의 render slot으로 책임을 숨기지 않는다. 새 옵션은 실제 의미·행동·데이터 관계의 차이를 나타내야 하며 임의 색·곡률·간격 선택지를 늘리지 않는다.

## 콘텐츠와 컨트롤의 조립

먼저 읽어야 할 정보의 구조를 만들고, 실제 조작을 적용 대상에 연결한다. 컨트롤이 없는 읽기 조합도 완성된 구성이다. 상태 배지나 읽지 않음 표식은 사실을 전달하며, 버튼·체크·선택기는 실제 조작 계약을 가진다. 표시 상태와 조작 상태를 섞지 않는다.

| 판단 대상 | 배치 기준 | 혼동하기 쉬운 경우 |
| --- | --- | --- |
| 콘텐츠 | 식별 → 이해 → 비교·판단의 읽기 순서와 데이터 관계 | 파일명·미리보기·작성자를 모두 입력 필드처럼 표현 |
| 컨트롤 | 적용 대상·범위, 사용 시점, 관련 명령의 관계 | 모든 카드에 보기·편집 버튼과 footer를 자동 추가 |
| 상태 | 대상의 상태는 대상 가까이, 실행·저장 상태는 해당 조작 가까이 | 업무 완료와 결과 생성 완료를 같은 check로 표현 |

컨트롤이 콘텐츠 가까이에 있어야 하는 경우도 있다. 업무 완료 체크는 해당 업무에, 값 편집은 해당 값에 연결한다. 컬렉션 전체의 필터와 정렬은 컬렉션 컨트롤에 둔다. 모든 행동을 전역 툴바로 옮기거나 모든 카드 안에 반복하지 않고 기존 컴포넌트의 계약과 실제 적용 범위를 따른다.

조립할 때 각 요소에 대해 “무엇을 판단하거나 조작하게 하는가, 왜 이 위치인가, 없애면 무엇이 모호해지는가”를 확인한다. 예를 들어 일정의 시간·제목·장소·참석자는 콘텐츠이고 참석 응답은 컨트롤이다. 시간의 우선순위와 참석 응답의 위치는 서로 다른 이유로 결정한다. 파일의 내용 미리보기와 ‘열기’도 같은 역할이 아니다. 카탈로그의 동작 시연이 콘텐츠 위계를 지배하지 않게 한다.

## 경계와 작은 단서

- 간격은 관련성, 선은 실제 반복 경계, 배경은 선택이나 다른 작업 영역, 박스는 독립 단위, 그림자는 실제 떠 있는 관계를 표현한다. 같은 구분을 여러 처리로 반복하지 않는다.
- 경계는 도메인 이름으로 고정하지 않는다. 콘텐츠끼리의 관계, 독립 단위, 입력 영역, 조작 그룹 중 무엇을 구분하는지 먼저 정한다. ‘일정은 면, 파일은 선’ 같은 한 사용례를 보편 규칙으로 굳히지 않는다. 기존 컨트롤의 곡률·높이·배경을 읽기 콘텐츠에 일괄 전파하지 않는다.
- 가장 가까운 공통 부모가 요소 사이 간격을 소유하고 실제 표면만 내부 padding을 가진다. 프로젝트의 간격 토큰과 margin 정책을 따른다.
- 아이콘은 대상·행동을, 배지는 실제 상태·분류·수를, 작은 인디케이터는 읽지 않음·변경 같은 실제 사실을 표현한다. 위치만으로 의미가 분명하면 추가하지 않는다.
- 깃발과 우선순위, 선택과 완료, 메시지 본문과 대화 기록을 혼동하지 않는다. 문의라는 이름만으로 채팅 버블을 선택하지 않는다.

## macOS 참고의 범위

macOS 참조가 요청되면 외형보다 창 → 탐색 영역 → 컬렉션 → 행·셀 → 상세 → 인스펙터의 책임과 슬롯을 검토한다. 아래는 Apple의 공식 사례이며 여러 생태계의 보편적 수렴을 증명하지 않는다. 네이티브 API·유리 효과·치수를 웹에 그대로 복제하지 않는다.

- [AppKit 테이블 구성](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/TableView/Introduction/Introduction.html): 컬렉션과 셀 책임 참고. 과거 문서이므로 현재 시각 디자인의 근거로 쓰지 않는다.
- [SwiftUI 인스펙터](https://developer.apple.com/videos/play/wwdc2023/10161/): 선택 콘텐츠의 보조 영역과 표시 상태.
- [AppKit의 새 디자인](https://developer.apple.com/videos/play/wwdc2025/310/): 툴바의 관련 명령 그룹과 정보·조작 구분.
- [Reminders](https://support.apple.com/guide/reminders/remndc729e28/mac): 완료·깃발·우선순위를 별개 의미로 취급.

카탈로그에서는 옵션 이름만 나열하지 말고 같은 구조의 읽기·편집·선택·빈 상태를 실제 데이터로 비교한다. 도메인 예시는 구조의 사용례이며 도메인별 정본을 반복 생성하는 근거가 아니다.


## 작업 단계와 시각적 중심

같은 화면에 존재하는 정보를 모두 항상 펼쳐 놓지 않는다. 요청을 읽을 때는 요청과 다음 행동, 실제 결과가 준비되면 결과와 후속 행동을 중심에 둔다. 원래 요청과 보조 속성은 기존 공개 펼침·패널 API로 다시 접근할 수 있게 보존한다. 실제 지원 상태와 전환만 사용하며 레이아웃을 위해 허위 진행·완료 상태를 만들지 않는다.

정보 위계에는 기존 제목·본문·보조 토큰을 선택한다. 주요 제목 하나가 읽기 영역의 중심을 맡고 작은 단서로 다른 상태를 구분한다. 크기·색·간격 변형을 새로 만드는 것으로 위계 문제를 덮지 않는다.

스크린샷은 수정 전과 수정 후에 같은 데이터·화면 크기로 비교한다. 요청/진행/결과처럼 실제 단계가 다르면 각각 확인한다. 무엇을 먼저 보게 되는지, 다음 행동이 분명한지, 보조 정보가 경쟁하는지, 좁은 화면의 제목 줄바꿈과 행동 위치가 유지되는지를 시각적으로 판단한다. 넘침 없음이나 DOM 일치만으로 좋은 디자인이라고 결론 내리지 않는다.
