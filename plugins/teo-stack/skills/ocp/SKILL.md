# OCP

실제 확장 시나리오에서 반복되는 소비자 수정을 줄인다. 목표는 확장 규칙을
한 소유자에 모으는 것이며, 분기 개수나 자동 등록 자체가 아니다.

리뷰 요청이면 분석과 제안을 제공한다. 구현이 요청되었거나 이미 승인되었다면
설계·전환·검증을 이어간다. 각 단계마다 별도 승인을 요구하지 않는다.

## 변경 이유부터 확인

어떤 항목을 추가하거나 삭제하는지, 그 집합이 실제로 확장되는지 확인한다.
그 시나리오에서 수정해야 할 정의, 등록, 소비자 위치를 나열하고 같은
책임 때문에 함께 바뀌는지 판단한다.

열린 집합의 같은 정책이 독립된 소비자 두 곳 이상에 흩어져 있으면 후보가
된다. 닫힌 집합의 exhaustive switch, 서로 다른 정책의 분기, 한 곳에서
완결되는 확장은 그대로 둘 수 있다.

수정 지점은 줄 수가 아니라 독립적으로 유지해야 하는 결정으로 센다.
한 등록 파일의 import와 엔트리는 보통 하나의 등록 지점이다.
서로 다른 판단을 숨긴 거대한 중앙 맵은 여전히 여러 변경 이유를 가질 수 있다.

## 가장 작은 확장 경계

함께 바뀌는 속성이 한 책임을 표현할 때 descriptor나 strategy로 모은다.
표현·검증·로딩처럼 서로 다른 책임이면 하나의 거대 descriptor로 합치지 않는다.

기존 정의 옆 배치, 명시적 맵, 기존 registry, strategy 중 가장 단순한
구조를 고른다. 명시적인 등록 한 곳은 유효한 결과다. 자기 등록이나
convention discovery는 실제 플러그인 계약과 초기화·순서·번들링 요구가
뒷받침할 때 사용한다.

필드는 필요한 값이나 동작만 표현한다. 모든 필드를 값-or-함수 union으로
만들거나 공용 resolve helper를 도입할 필요는 없다.

소비자가 확장 항목별 정책을 중복 소유하지 않게 한다. 범용 validation,
상태 분기, 권한 확인, 명시적 unsupported 처리는 남을 수 있다.
알 수 없는 타입을 정상 값으로 조용히 대체하지 않는다.

## 구현과 검증

확장 책임을 소유자에 옮기고 해당 소비자와 import를 갱신한다. 기존 동작과
실제 public contract를 보존한다.

같은 추가·삭제 시나리오를 전후로 비교한다. 항목 자체의 정의를 제외한
소비자 수정은 0곳, 명시적 등록은 0~1곳을 지향하되 이를 맞추려고
간접 참조나 다른 책임의 결합을 늘리지 않는다.

기존 variant 동작, unknown 처리, 저장소 필수 검사를 확인한다.
실제로 줄어든 동반 수정, 선택한 구조의 이유, 검증과 남은 제약을 보고한다.
