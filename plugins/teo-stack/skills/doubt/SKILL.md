# Doubt

필요한 결과를 유지하면서 개념과 절차를 줄인다. 삭제·통합으로 코드량을 줄이되, 줄 수나
파일 수 감소만으로 성공을 판정하지 않는다.

리뷰·질문이면 판단과 근거를 제공한다. 정리·축소를 요청했거나 이미 실행을
승인했다면 범위 안에서 수정하고 검증한다.

## Code reduction

리팩토링과 기존 코드 수정은 항상 코드량을 줄이는 방향으로 수행하며, 계약·동작을 보존한 전체 수기 작성 코드 순증 0 이하를 완료 기준으로 삼는다. 작은 수정에서 코드량을 유지하는 것은 허용한다. 새로운 기능 추가 요청에 이 기준을 기계적으로 적용하지 않는다.

- 먼저 기존 구현의 수정·삭제·통합으로 해결한다. 대체한 옛 구현, 중복 분기·타입·상태와 불필요한 wrapper·adapter·facade를 같은 변경에서 제거한다. 구조를 나눴다는 이유만으로 보조 코드를 늘리지 않는다.
- 작업 시작 상태를 기준으로 이 작업의 전체 변경을 센다. 새 파일·소비자·import·CSS·test·mock·guard도 포함하고 production과 검증용 코드의 추가·삭제·순증을 나누어 보고한다. 문서·생성물은 따로 표시하며 그 삭제로 코드 증가를 상쇄하지 않는다. 다른 사람의 변경은 계산과 정리에서 제외한다.
- 파일 이동·재분할, 줄 합치기·포맷 압축, 다른 계층으로의 복잡도 이동은 축소가 아니다. 숫자를 맞추려고 필요한 기능·외부 계약·오류 관측·검증을 없애거나 무관한 코드를 삭제하지 않는다.
- 순증이면 완료 전에 더 작은 해법을 다시 검토한다. 필수 동작이나 검증 때문에 증가를 피할 수 없다면 최소 증가분과 줄일 수 없는 구체적 이유를 보고하고, 축소 기준을 충족했다고 말하지 않는다. 단순히 “구조가 좋아졌다”는 증가 근거가 아니다. 필수 증가의 근거와 검증이 확보되면 수정은 완료할 수 있지만, 축소 기준 미충족을 별도로 보고하고 무관한 축소 작업으로 범위를 넓히지 않는다.

## 새 구조를 검토할 때

기존 메커니즘으로 필요한 동작을 표현할 수 있는지, 새 경계가 어떤 책임이나
불변식을 소유하는지 확인한다. 작은 기존 수정과 새 구조의 의존성·이해 비용을
비교한다. 기존 구조를 억지로 늘리는 것보다 새 경계가 단순할 수도 있다.

미래 재사용이나 예외 가능성만으로 flag, wrapper, workflow를 추가하지 않는다.
현재 요구사항에 필요한 개념은 소비자가 하나여도 정당할 수 있다.

## 정리할 때

대상의 역할과 존재 이유를 확인하고 다음 질문으로 판단한다.

- 아직 필요한가?
- 책임에 맞는 형태인가?
- 같은 의미를 더 적은 구조나 반복으로 표현할 수 있는가?
- 줄인 복잡도가 다른 소비자나 숨은 절차로 이동하지 않는가?

의문이 있는 항목은 호출부, 계약, 테스트, 역사에서 이유를 찾는다.
불확실하고 제거 위험이 크면 유지하며 빠진 증거를 보고한다.
숫자나 목록을 완성하려고 유지 항목까지 전부 나열할 필요는 없다.

## 실행과 검증

근거가 있는 제거·축소·병합을 수행하고, 유지할 계약과 관측 가능한 실패 상태를
보존한다. 현재 작업과 무관한 사용자 변경을 함께 정리하지 않는다.

변경된 의미와 의존 경계를 검증하고 저장소 필수 검사를 완료한다.
단순하고 되돌릴 수 있는 변경에 구현을 그대로 따라 쓰는 테스트를 추가하지 않는다.

삭제·통폐합이나 순증 축소가 목적이면 production 코드뿐 아니라 소비자·
adapter·test·mock·guard·문서·생성물까지 전체 변경을 본다. 코드를 옮기거나
보상 코드로 대체한 것을 복잡도 제거로 세지 않는다. 새 간접 계층 때문에
이해·변경 비용이 커졌다면 그 변경을 재고하고, 되돌릴 때는 이 작업의 변경만
대상으로 한다. 필요한 계약·검증·실패 관측을 숫자를 줄이기 위해 없애지 않는다.

결과에는 줄이거나 유지한 중요한 항목, 이유, 검증을 남긴다. 순증을 질문받으면
전체 diff의 추가·삭제 규모와 필요한 증가 이유를 설명하고, production 변경과
test·문서·생성물 증가를 구별한다. 그 외에는 숫자나 정해진 표가 판단에 도움이
될 때만 사용한다.
